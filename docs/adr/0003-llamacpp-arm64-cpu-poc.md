# ADR 0003: RK3588 CPU PoC 使用独立 llama.cpp Provider

- 状态：Accepted
- 日期：2026-08-08

## 背景

首轮 RK3588 验证的目标是证明“单个本地模型 + Agent + Web 操作台”能在 8GB ARM64 设备上启动并完成文本请求。目标设备尚未配置 RKNPU/RKLLM，且两个模型不能同时常驻内存。现有 `ollama` 和 `rkllm` Provider 都不能准确表达该运行边界。

## 决策

1. 新增 `llamacpp` Provider，调用容器内仅监听回环地址的 llama.cpp OpenAI 兼容接口，并继续执行 Agent 现有的结构化 JSON 协议与 Schema 校验。
2. Qwen2.5-3B-Instruct Q4_K_M 与 LFM2.5-1.2B-Instruct Q4_K_M 分别生成一个 ARM64 CPU 镜像。两个镜像共享运行时结构，但每个镜像只包含一个模型，部署时串行运行。
3. 线程、上下文、输出上限、批大小和并发全部由环境变量控制。启动档只用于首次可运行验证，不构成产品上限。
4. `general_chat` 是 R0/D0 的模型工具。确定性算术在工具内计算；其他通用问题通过模型生成 `answer` 字段。知识库只有在检索为空且请求不包含本地资料、组织制度或来源约束时，才允许回退一次到 `general_chat`。
5. 真机性能结论必须由板端脚本测得。没有真机数据时，镜像只能标记为 PoC 候选，不能标记为已通过 RK3588 验收。

## 不变量

- 知识库有命中时必须保留来源，不得被通用回答覆盖。
- 明确要求查询本地文档、知识库、公司制度或来源的请求，检索为空时不得无来源回退。
- `general_chat` 不持久化业务数据，不调用其他工具，不接受模型提示词或占位符回显作为有效结果。
- llama.cpp 服务只在容器回环地址监听，外部只暴露 Agent Web/API 端口。
- 性能对比一次只运行一个模型和一个线程配置。

## 后果

CPU 数据可以作为后续 Qwen RKNPU/RKLLM 加速的可比基线。代价是镜像体积包含单个 GGUF 模型，并且 CPU 吞吐、首字延迟和温度只能在实际交换机上确定。
