## 1. 结论摘要

本轮不是只测“模型是否能返回 JSON”，而是分两层验证：

1. 60 条固定用例验证意图、参数、Schema、归一化契约和 dry-run 端到端结果。
2. 每个模型使用独立临时数据库和授权资源，真实执行知识、文件、提醒、待办、日程、文本、会议 7 类业务流程。

三个模型共同稳定通过知识检索、授权文件候选和会议纪要流程。Qwen2.5 另外稳定通过待办和文本；Qwen3 另外稳定通过文本；LFM 的严格文本质量未通过。提醒、待办和日程的主要风险不是 SQLite 或工具崩溃，而是小模型输出非法 JSON、把可选字段误报为必填缺失，或把时间/动作放进错误字段。系统均按现有安全边界停止，没有未经确认的破坏性执行。

## 5. 工具层与模型层归因

### 确定性工具控制项

- 中文/财务大写数字日程直接进入工具时，三个运行均得到 `2026-08-08T09:00:00+08:00` 至 `2026-08-08T10:00:00+08:00`。
- “清空全部提醒”现在稳定归一化为 `{"action":"delete_all"}`，并有自动化测试。
- 知识、文件、提醒、待办、日程和会议都使用独立临时数据，未复用当前 8000 服务的数据库。

因此，日程错日期/丢结束时间、Qwen3 的冗余 `missing_fields`、LFM 的动作误判和文本占位符泄露属于模型输出或模型到工具参数契约问题，不应继续归因于本地数据库、授权根路径或业务工具本身。

### 复测中补的代码缺口

初次实测发现现有规则只覆盖“清空提醒/删除全部提醒”等说法，未覆盖“清空全部提醒”。本轮已补充该确定性归一化规则和回归断言。补丁解决了本地参数规则缺口，但不会伪造模型遗漏字段；真实模型仍可能安全停在缺字段状态。

## 6. 推荐与后续优先级

1. 当前三者中，`qwen2.5:3b` 仍是默认候选，但必须带着提醒清空和日程结束时间两个已知缺口使用，不能写成 7/7 或“全功能可用”。
2. P0：在不放宽工具必填字段的前提下，用 `ToolMetadata` Schema 对模型的 `missing_fields` 做确定性裁决；参数已经满足当前动作时，应忽略模型误报的可选字段。
3. P0：日程创建阶段增加 `range_end -> end_text` 和请求原文时间段恢复，避免模型把结束时间放错字段或丢失日期。
4. P1：文本结果增加占位符/不可读内容质量门禁；失败时受控重试或回退，不能把 `<FACT_n>` 暴露给用户。
5. P1：把“清空全部提醒”、中文大写日期起止时间、待办状态更新加入固定模型评测集，避免 60 条总分掩盖专项退化。
6. Qwen3/LFM 在上述 P0 修复和专项盲测前，不建议作为默认模型；较小参数量或较快裸生成速度不能替代 Agent 端到端正确率。
