# 功能扩展③：日程管理工具（开发提示词 v2）

> 设计书 MVP 要求：“提醒、日程与待办”形成完整工具。
> 本任务实现本地日程、有限范围的重复规则和可靠通知；不接入外部日历，不修改 Agent Core 状态机。

---

## 可直接执行的开发任务

在 `D:\my new work\cloud flowing` 实现 `schedule_manage`。先阅读当前 `ReminderTool`、容器的后台任务生命周期、策略规则、模型接收 Schema、参数归一化和测试。沿用本地优先架构：Qwen2.5-3B-Instruct 只识别意图/字段，确定性代码解析时间、展开重复、控制确认和发送通知。

### 目标

新增可持久化日程工具，支持创建、范围查询和按唯一 ID 取消；支持 daily、weekly、monthly 重复，按请求范围动态展开，并对每个日程实例最多发送一次本地 Toast 通知。

### 分阶段交付顺序

按以下顺序实现并在每阶段保留测试；后续阶段不得破坏前一阶段。

1. 一次性日程：创建、查询、按 ID 取消、重启持久化。
2. 重复规则：daily、weekly、monthly 的有界展开。
3. 通知：容器启动/关闭生命周期、持久化去重和固定时钟测试。

### 工具与严格 Schema

工具名为 `schedule_manage`，操作为 `create`、`query`、`cancel`。

输入字段：`action`、`id`、`title`、`title_query`、`start_text`、`end_text`、`location`、`recurrence`、`weekdays`、`recurrence_until_text`、`range`、`range_start`、`range_end`、`notify_before_minutes`。

严格执行契约：

1. `create` 必须有 `title` 和 `start_text`；时间解析后得到带时区的 `start_at`。`end_text` 存在时必须解析且严格晚于 `start_at`。
2. `cancel` 必须有正整数 `id`。按标题、日期等自然语言取消请求必须先形成 `query` + `title_query`，返回候选日程；不得直接取消同名日程。
3. `query` 的 `range` 仅允许 `today`、`tomorrow`、`this_week`、`next_week`、`custom`；`custom` 时 `range_start`、`range_end` 必填，范围最长 31 天。
4. `recurrence` 仅允许 `none`、`daily`、`weekly`、`monthly`，默认 `none`。`weekly` 必须有非空、去重且值在 0-6 的 `weekdays`；`monthly` 使用 `start_at` 的日期作为每月触发日。
5. `recurrence_until_text` 是可选上界；未给出时，查询仍必须受 31 天和 500 个实例的双重上限。达到上限时返回明确截断状态，不能无限循环或静默遗漏。
6. `notify_before_minutes` 默认为 15，允许 0-1440 的整数。
7. 解析失败、缺少必填字段、开始结束时间倒置时必须走缺字段/错误结果，不得创建记录。

### 数据与重复实例模型

使用独立 `schedules.db`，沿用当前 `settings.database_path.with_name(...)` 路径约定。至少建立：

```text
schedules(
  id, title, location,
  start_at, end_at,
  recurrence, weekdays_json, recurrence_until_at,
  status, notify_before_minutes,
  created_at, cancelled_at
)

schedule_notifications(
  schedule_id, occurrence_start_at, notified_at,
  PRIMARY KEY(schedule_id, occurrence_start_at)
)
```

所有时间以 ISO 8601（含时区）存储。一次性日程的实例就是自身；重复日程实例由“原始 start_at 的时间部分 + 每个规则允许的日期”确定。展开逻辑只使用表中真实字段，不能依赖未存储的 `time_offset`、`original_day` 或虚构的 `start` 字段。

开启 SQLite WAL 和 busy timeout，所有状态写入与通知去重写入使用事务。取消只更新 `status='cancelled'` 和 `cancelled_at`，不物理删除。

### 时间解析边界

1. 将可复用的数字规范化和时区处理抽取到提醒/日程共用的确定性解析组件；不能复制两套解析器。
2. 必须支持本任务固定用例：`明天下午2点`、`明天下午2点到4点`、`每天下午3点`、`每周一三五上午9点`、`每月5日 10 点`、`今天/明天/本周/下周`范围。
3. 不支持的表达式（例如没有时间的“下周开会”）必须要求补充信息。不得引入未声明的第三方时间解析服务，也不得让模型猜测 ISO 时间。
4. 解析 API 接受注入的 `now` 和时区，测试不得依赖机器当前时间。

### 风险、确认与通知

1. 工具基础风险为 `R1`；在 `policy_rules.yaml` 中将 `schedule_manage` 的 `action=cancel` 升级为 `R2` 并要求执行前确认。确认内容必须包含日程 ID、标题和开始时间。
2. 取消操作不得在工具内部“先改状态再确认”。策略引擎确认后，工具才可执行。
3. 容器在初始化时启动通知调度，在关闭时停止并等待任务退出；不要创建不可管理的无限协程。
4. 通知轮询根据当前窗口计算日程实例；向 `schedule_notifications` 成功插入去重键后才调用 `windows_toast`。同一实例在轮询、重启或重试后最多通知一次。
5. 只做本地 Toast，不新增外部推送、日历同步、账号登录或网络访问。

### 当前架构接入点

1. 新增 `agent_platform/tools/schedule_tool.py` 并从工具包导出；在 `ApplicationContainer` 创建、注册、初始化和关闭它。
2. 在 `agent_platform/models/model_schema.py` 的 `INTENT_NAMES` 中加入 `schedule_manage`，由现有 ToolMetadata 动态生成模型接收 Schema。不要创建或修改不存在的 `models/model.py`。
3. 必要时重平衡 `cloud_adapter.py` 的完整 intent few-shot，使总示例不超过 8 个；日程只保留“创建/重复”和“范围查询/按 ID 取消”两类代表性示例。模型提示词不得承担时间计算和确认决策。
4. 仅对明确中文模式添加参数归一化；例如“今天下午有什么安排”归一化为 `range=today`。不能从标题推断或伪造 ID。
5. 不修改 Agent Core 状态机、通用执行器、通用 SchemaValidator 或既有工具的 `execute()`。

### 自动化验收

使用固定时钟，新增不少于 12 个测试，至少覆盖：

1. 一次性创建、查询排序、重启持久化和开始结束时间校验。
2. daily、weekly 多星期和 monthly 展开，`recurrence_until` 边界，以及 31 天/500 实例上限。
3. `today`、`tomorrow`、`this_week`、`next_week`、`custom` 查询范围。
4. 同名日程的按标题取消请求只返回候选；按 ID 取消进入 `awaiting_confirmation`，确认前无 `TOOL_CALLED`，确认后仅状态变为 cancelled。
5. 每个 occurrence 的通知只触发一次，容器关闭后不再轮询，重启后不重复通知。
6. 不可解析时间、无 title/start、非法 weekdays、倒置结束时间和超范围 custom 查询均无副作用。
7. 至少 5 条固定日程评测用例，使用干跑验证执行结果及确认状态。

运行完整 `pytest`，以当前 `206` 项通过为无回归基线；既有 50 条评测端到端准确率不得低于当前 90%。新增日程固定集在同一真实模型环境中端到端准确率目标为 80% 以上；低于目标时优先修复 few-shot、Schema 和确定性归一化，不能放宽取消确认或执行 Schema。

### 停止条件与交付

只有在三阶段功能、严格字段约束、执行前取消确认、重复展开上限、通知持久化去重和所有自动化验证均通过时完成。交付修改文件、表结构说明、测试命令与结果，以及创建、候选查询、取消确认和单次通知的脱敏任务结果示例。
