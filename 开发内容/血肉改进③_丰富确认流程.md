## 开发提示词

### 目标
在 Mock 适配器和 Policy Engine 中增加演示场景，使确认流程（awaiting_confirmation）在演示时能被充分展示。目前只有 meeting_process 缺 source_path 会触发确认，需要增加：文件多候选选择、高风险操作二次确认、参数歧义澄清。不修改架构，只丰富 Mock 数据和策略规则。

### 判断标准

1. **文件多候选**：当 Mock 适配器收到的 query 是模糊关键词（如「周报」而非「项目周报_20260721」）时，`file_open` 工具返回多个候选文件让用户选择
2. **高风险确认**：定义一条策略规则——当操作为 `reminder_create` 且 action 为 `delete_all` 时，风险等级 R3，必须用户二次确认
3. **参数歧义**：当用户说「提醒我明天开会」但未指定具体时间时，reminder_create 将 `time` 标记为 missing_field，触发参数补填确认
4. 所有确认场景在确认通过后任务继续执行并正确完成，确认拒绝后任务进入 cancelled

### 证据要求

- 输入「打开周报」→ 进入 awaiting_confirmation → 显示 3 个候选文件 → 选择一个确认 → 打开成功
- 输入「删除所有提醒」→ 进入 awaiting_confirmation → 显示 R3 风险警告 → 确认 → 执行 → 取消 → cancelled
- 输入「提醒我明天开会」→ 进入 awaiting_confirmation → 显示 time 字段缺失 → 填入「15:00」确认 → 提醒创建成功
- 确认拒绝测试：在确认面板点取消 → 任务状态变为 cancelled → 审计日志记录拒绝原因

### 权限边界

- 只在 MockAdapter 和 PolicyEngine 的配置文件/规则中修改
- 不修改任务状态机的核心流转逻辑
- 不修改 Tool Executor 的执行逻辑
- 新增的策略规则写入配置文件，不硬编码

### 停止条件

- 3 个确认场景各测试一次，全部通过
- 确认通过路径：awaiting_confirmation → executing → completed
- 确认拒绝路径：awaiting_confirmation → cancelled
- 审计日志中正确记录了确认/拒绝事件
- 文件多候选场景中，候选列表包含至少 2 个文件，且文件名和修改时间真实可辨

### 完成边界

改动的文件：`agent_platform/adapters/mock_adapter.py`（丰富 intent 输出）、`agent_platform/config/policy_rules.yaml`（如有，新增 R3 规则）、`agent_platform/tools/file_search_tool.py`（返回多候选而非直接选第一个）。

### 实现指引

**Mock 适配器改动（file_open 多候选）：**

当前 `file_open` 意图的 arguments 只包含 `query`。修改为：当 query 模糊时，在 arguments 中附加 `candidates` 列表和 `requires_confirmation: true`。

```python
# 伪代码
if intent == "file_open" and is_ambiguous(query):
    result["arguments"]["candidates"] = [
        {"name": "项目周报_20260721.docx", "modified": "2026-07-21", "path": "..."},
        {"name": "项目周报_20260714.docx", "modified": "2026-07-14", "path": "..."},
        {"name": "项目周报模板.docx", "modified": "2026-06-01", "path": "..."},
    ]
    result["arguments"]["requires_confirmation"] = True
```

**Mock 适配器改动（reminder 时间歧义）：**

当提醒请求包含「明天」但没有具体时间时，将 `time` 标记为 missing_field：

```python
if intent == "reminder_create" and "明天" in text and not has_specific_time(text):
    result["missing_fields"] = ["time"]
```

**Policy Engine 改动（R3 规则）：**

在 `config/policy_rules.yaml` 中添加：

```yaml
- name: delete_all_reminders
  action_pattern: "reminder_create"
  argument_conditions:
    action: "delete_all"
  risk_level: R3
  requires_confirmation: true
  confirmation_message: "即将删除所有提醒，此操作不可撤销。确认继续？"
```

### CloudAdapter 改动（cloud 模式下的确认触发）

在 `agent_platform/adapters/cloud_adapter.py` 的分类 system prompt 末尾追加确认触发规则，使 DeepSeek 在特定场景下返回 missing_fields：

```python
# 在分类 prompt 的 Intents 列表之后、"If required arguments" 之前追加：
"Confirmation rules:\n"
"- For file_open with vague keywords without date (e.g. just '周报'), include candidates in arguments and add 'confirm_file' to missing_fields\n"
"- For reminder_create with a date but no specific time, add 'time' to missing_fields\n"
"- Do NOT fabricate missing fields for clear, complete requests\n\n"
```

## 代码审查提示词（质量）

检查项：
1. Mock 适配器新增的候选列表是否在 Tool Executor 的回执校验中正确通过
2. R3 确认规则是否在 Policy Engine 的所有路径上都有覆盖（直接执行、确认后执行、拒绝执行）
3. missing_fields 的参数补填是否支持所有字段类型（字符串、枚举、布尔）
4. 确认流程中如果用户提供的参数仍然不合法，是否重新进入确认而非静默失败

检查项：

3. Mock 适配器中的演示数据是否与生产逻辑隔离（可通过配置开关控制）
