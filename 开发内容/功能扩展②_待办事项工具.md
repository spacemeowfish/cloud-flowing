# 功能扩展②：待办事项工具（开发提示词 v2）

> 设计书 MVP 要求：“提醒、日程与待办”形成完整的本地效率工具。
> 本任务只新增本地待办能力；不接入第三方任务服务，不修改 Agent Core 状态机。

---

## 可直接执行的开发任务

在 `D:\my new work\cloud flowing` 实现 `todo_manage` 工具。先阅读当前工具注册、模型接收 Schema、参数归一化、策略规则、提醒时间解析器和测试，再开始编辑。保持“模型理解，确定性工具校验、执行、审计和确认”的边界。

### 目标

新增持久化的待办管理工具，支持创建、查询、更新、完成和删除；所有状态变更按唯一 ID 执行，删除必须在工具执行前经策略引擎确认。

### 工具契约

工具名为 `todo_manage`，操作为：`create`、`query`、`update`、`complete`、`delete`。

严格执行 Schema 的规则：

1. `create` 必须有 `title`。
2. `update`、`complete`、`delete` 必须有正整数 `id`；`update` 还必须至少包含一个允许更新的字段。
3. `query` 可使用 `status`、`priority`、`tag`、`title_query`、`due_from`、`due_to` 过滤；无过滤时默认返回 `pending` 与 `in_progress`。
4. `priority` 仅允许 `high`、`medium`、`low`；`status` 仅允许 `pending`、`in_progress`、`completed`。
5. `tags` 是字符串数组，存储为 JSON，读出仍为数组。
6. 时间字段使用 `due_at`，持久化为带时区 ISO 8601；输入阶段允许 `due_text`，由确定性时间解析器转换。解析失败时走缺字段确认，不写入数据库。
7. `delete` 只允许按 ID 删除；“删除/完成交报告”这类按标题的自然语言请求必须先转换为 `query` + `title_query`，返回候选 ID，不能直接修改任意同名待办。

建议的模型输出字段为：`action`、`id`、`title`、`description`、`priority`、`tags`、`status`、`due_text`、`title_query`、`due_from`、`due_to`。模型接收契约可接受缺少 ID 的部分结果以发起澄清，但严格工具 Schema 必须在执行前拒绝它。

### 数据与时间边界

1. 使用独立的 `todos.db`，路径遵循现有 `settings.database_path.with_name(...)` 模式；不要与提醒表或任务会话表复用连接。
2. 建立 `todos` 表：`id`、`title`、`description`、`priority`、`tags`、`status`、`due_at`、`created_at`、`updated_at`、`completed_at`。对 priority 和 status 设 SQLite `CHECK` 约束。
3. 打开 SQLite WAL 和合理的 busy timeout；所有写入在事务内完成。
4. 复用并按需小范围扩展 `ChineseTimeParser` 的数字/时区能力，不能复制第二套中文时间解析器。扩展“下周星期 X”时，必须同时补齐提醒工具的兼容测试；无法确定具体时刻时要求用户补充，不能默认一个时间。
5. 任务创建、完成、更新和删除必须生成稳定的幂等键；查询不应意外复用过期结果。

### 风险与确认

1. 工具基础风险设为 `R1`。
2. 在 `policy_rules.yaml` 增加 `todo_manage` 的 `action=delete` 规则：风险 `R2`、需要确认、可逆为 false，并给出包含待办 ID 的确认文案。
3. 确认必须由 Agent Core 在调用工具前完成；工具的 `delete()` 不得先删除再返回确认信息。
4. `complete` 和 `update` 仅对明确 ID 生效；找不到 ID 必须返回无副作用的结果。

### 当前架构接入点

1. 新增 `agent_platform/tools/todo_tool.py`，并从 `agent_platform/tools/__init__.py` 导出。
2. 在 `ApplicationContainer` 创建、注册、关闭该工具；将其放入现有 `ToolRegistry` 冻结前的工具列表。
3. 在 `agent_platform/models/model_schema.py` 的 `INTENT_NAMES` 中加入 `todo_manage`。模型接收 Schema 从 ToolMetadata 动态导出，不创建或修改不存在的 `models/model.py`。
4. 必要时重平衡 `cloud_adapter.py` 的完整 intent few-shot，使总示例不超过 8 个；待办只保留“创建”和“按标题查询候选/按 ID 状态变更”两类代表性示例。不得复制一份静态工具 Schema 到提示词中。
5. 仅为确定性、按意图白名单的别名或优先级映射修改 `parameter_normalizer.py`；不让模型或归一化器猜测待办 ID。
6. 不修改 Agent Core 状态机、通用 SchemaValidator、工具执行器或既有工具的 `execute()`。

### 必测场景

以固定时钟运行自动化测试，至少覆盖：

1. 创建高优先级待办，时间可解析并持久化。
2. 无截止时间创建待办，不虚构 `due_at`。
3. 默认查询不返回 completed；状态、优先级、标签和截止范围过滤正确。
4. `update`、`complete` 对明确 ID 正确修改，未知 ID 无副作用。
5. 同名待办时按标题请求完成只返回候选，不修改数据。
6. `delete` 进入 `awaiting_confirmation`，确认前不存在 `TOOL_CALLED` 或数据删除；确认后只删除指定 ID。
7. 重启容器后记录仍可查询。
8. Schema 条件必填、SQLite 约束、WAL 初始化和标签 JSON 往返正确。
9. 至少 5 条固定待办评测用例覆盖上述意图；离线/Mock 干跑验证执行结果与确认状态。

运行完整 `pytest`，以当前 `206` 项通过为无回归基线；新增测试全部通过。既有 50 条评测端到端准确率不得低于当前 90%，新增待办固定集在同一真实模型环境中的端到端准确率目标为 80% 以上；低于目标时先修正 Schema、few-shot 或确定性归一化，不以放宽严格执行 Schema 取分。

### 停止条件与交付

仅在五种操作满足严格契约、删除确认发生在执行前、数据重启后仍存在、全部自动化验证通过时完成。交付修改文件、迁移/表结构说明、测试命令与结果，以及创建、候选查询、删除确认三个脱敏任务结果示例。
