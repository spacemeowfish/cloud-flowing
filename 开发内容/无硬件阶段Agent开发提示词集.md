> 基于 V0.7 部署评估报告 + Codex 架构（已补充数据分级/离线队列/资源监控/连接器管理/会话持久化）

## 使用说明

### 模块依赖关系

```
Phase 1 基础层（全部并行）
  F1 项目骨架       ─┬─ 无上游依赖
  F2 模型网关       ─┤
  F3 任务状态机     ─┤
  F4 工具注册执行   ─┤
  F5 权限数据分级   ─┤
  F6 路由离线资源   ─┤
  F7 连接器管理     ─┤
  F8 审计评测       ─┘

Phase 2 工具层（依赖 F3 F4 F5 F6 F7，工具之间并行）
  T1 文件工具       ─┬─ 无工具间依赖
  T2 知识库工具     ─┤
  T3 提醒待办工具   ─┤
  T4 短文本工具     ─┤
  T5 会议纪要管线   ─┘

Phase 3 集成层（依赖 Phase 1 + 2）
  I1 Agent Core    ─┬─ 依赖全部 Phase 1 + 全部 Phase 2
  I2 FastAPI 服务   ─┤
  I3 自动化评测集   ─┘
```

### 审查策略

每个模块开发完成后，并行启动 3 个子 Agent 分别审查代码质量、性能和复用性。审查结果必须与 IDEA 标准对齐。

## F1：项目骨架与数据协议

### 开发提示词

#### 目标
搭建 Python 项目骨架，定义全部 Pydantic 数据模型和抽象接口（ABC），为所有后续模块提供统一的类型系统。不包括任何业务逻辑实现，只定义数据形状和接口契约。

#### 判断标准

1. 所有数据模型使用 Pydantic v2 定义，字段类型完整、必填/可选明确
2. 所有抽象接口（ModelAdapter / Tool / Policy / Router 等）使用 ABC 定义，方法签名与架构文档一致
3. 配置管理支持环境变量和 .env 文件覆盖
4. 包结构清晰：`core/`（抽象接口）、`models/`（数据模型）、`config/`（配置）、`adapters/`（适配器占位）
5. `pip install -e .` 可安装，`pytest` 可运行（即使只有骨架测试）

#### 证据要求

- 交付完整的目录结构和 `pyproject.toml`
- 每个 Pydantic model 有对应的单元测试验证序列化/反序列化
- 每个 ABC 接口有文档字符串说明契约
- 配置类支持从 `.env` 加载，并提供默认值

#### 权限边界

- 只创建文件和目录，不执行任何系统命令或网络请求
- 不安装依赖（只声明在 pyproject.toml 中）
- 不引入任何具体模型调用代码

#### 停止条件

- 运行 `python -c "from agent_platform.models import *; from agent_platform.core import *"` 无 ImportError
- 运行 `pytest` 全部通过（骨架测试数量 ≥ 数据模型数量）
- pyproject.toml 中 dependencies 列表完整

#### 检索边界

搜索最新 Pydantic v2 和 ABC 用法时，仅验证 API 签名是否与最新稳定版一致，不引入未声明的第三方库。

#### 行动边界

可直接创建目录和文件。不修改已有的架构文档.md。不确定的模型字段参考部署评估报告的数据结构和架构文档的模块定义。

#### 完成边界

所有模型文件包含 `__all__` 导出列表。`pyproject.toml` 中包含 `[project.scripts]` 占位入口。`tests/` 下每个模型文件有对应测试。

- D: 架构文档全部模块定义
- E: 修改建议需要给出替代方案，不单纯否定
- A: 输出复用性评分（0-10）和改进清单

## F2：模型网关

### 开发提示词

#### 目标
实现 Model Gateway 和两个适配器：MockModelAdapter（返回固定结构化 JSON，供测试用）和 CloudModelAdapter（调用当前云端模型 API）。确保上层代码只依赖 `ModelAdapter` 抽象接口，不感知具体模型实现。

#### 判断标准

1. `ModelAdapter.generate()` 接口与架构文档 §3 一致：输入 messages + response_schema + max_tokens，输出 dict
2. 通过环境变量 `MODEL_PROVIDER` 切换适配器，默认 `mock`
3. MockAdapter 的响应结构完全符合架构文档 §6 的 JSON Schema（intent / arguments / missing_fields / confidence）
4. CloudAdapter 正确处理 API 超时、限流和格式错误，转换为统一的 ModelError
5. 每个适配器有独立的单元测试，MockAdapter 的测试覆盖所有预定义场景

#### 证据要求

- `MockModelAdapter` 至少支持 5 种预定义意图（文件打开、知识查询、提醒创建、文本润色、会议纪要）
- `CloudModelAdapter` 的测试使用 VCR/mock HTTP 模式，不依赖真实 API Key
- 切换 `MODEL_PROVIDER` 后，同一个 Agent 调用无需修改任何代码
- `ModelError` 包含 `retryable: bool` 和 `detail: str`

#### 权限边界

- CloudAdapter 的 API Key 从环境变量读取，不允许硬编码
- 不向云端发送任何模拟用户数据（测试只使用示例文本）
- 不在日志中记录完整的 API 请求/响应体（只记录元数据）

#### 停止条件

- `python -m pytest tests/test_model_gateway.py -v` 全部通过
- MockAdapter 覆盖所有 5 种预定义意图
- CloudAdapter 正确处理超时（mock）、限流（429）、和格式错误（返回非 JSON）
- ModelGateway 的 `generate()` 方法签名与 F1 中的 ABC 一致

#### 完成边界

交付文件清单：`core/model_gateway.py`、`adapters/mock_adapter.py`、`adapters/cloud_adapter.py`、`tests/test_model_gateway.py`。每个 Python 文件尾部有 `if __name__ == "__main__":` 的 smoke test。

---

### 代码审查提示词（质量）

检查项：
1. MockAdapter 的响应是否每个字段都符合 Schema（不允许返回 Schema 未定义的字段）
2. CloudAdapter 的 HTTP 错误处理是否覆盖了：连接超时、读取超时、429 限流、500 服务端错误、返回非 JSON 内容
3. `ModelError` 的子类是否正确区分了可重试和不可重试错误
4. 异步调用是否正确使用了 `async/await` 和 `httpx.AsyncClient` 的上下文管理

IDEA：依据架构文档 §3 的接口定义和部署评估报告 §5 的端云任务链。出逐条检查结果。

---

### 代码审查提示词（性能）

检查项：
1. CloudAdapter 的 HTTP 连接是否复用了连接池（不应每次调用新建连接）
2. MockAdapter 的响应生成是否有不必要的 I/O 或计算开销
3. `generate()` 方法的参数校验是否在异步路径之外完成（避免不必要的协程调度）

IDEA：MockAdapter 因为是开发期主力调用路径，高频调用下的性能影响会被放大。

---

### 代码审查提示词（复用性）

检查项：
1. 新增适配器是否只需实现 `ModelAdapter` 抽象接口的三个方法，不需要修改网关代码
2. 网关的错误转换逻辑是否独立于适配器实现
3. `response_schema` 的传递方式是否允许未来扩展（如支持多个 schema 的联合校验）

## F3：任务状态机 + 会话持久化

### 开发提示词

#### 目标
实现 Task API、Task State Machine 和 Session Manager。Task API 接收用户请求并创建任务编号，状态机管理任务生命周期（接收→理解→校验→确认→执行→交付→完成/失败/取消），Session Manager 负责 SQLite 持久化和应用重启后的状态恢复。

#### 判断标准

1. 任务状态流转严格遵循部署评估报告 §5 的 7 步任务链，非法状态转换抛出明确错误
2. 每个状态的变更立即写入 SQLite（WAL 模式），不使用内存缓存延迟写入
3. 应用重启后，所有未完成的任务（非 completed/cancelled/failed 终态）自动恢复到内存状态机
4. 任务支持用户取消，取消后工具执行被中断，状态记录为 cancelled
5. 并发安全：同一任务的状态变更使用乐观锁（version 字段），冲突时重试一次

#### 证据要求

- 完整的状态转换测试覆盖所有合法路径和 10+ 种非法路径
- 持久化恢复测试：创建任务→模拟进程终止→重新初始化→验证任务状态和上下文一致
- 取消测试：执行中的任务被取消后，工具执行器收到取消信号（通过 asyncio.Event）
- 并发测试：两个协程同时更新同一任务，第二个被乐观锁拒绝或重试

#### 权限边界

- SQLite 文件路径由配置文件指定，不可硬编码
- 不允许多个 Agent 实例同时打开同一个 SQLite 数据库（使用文件锁检测）
- 任务数据不包含任何敏感字段的明文存储（如果有，使用 F5 的脱敏服务处理，但本模块不直接处理脱敏逻辑）

#### 停止条件

- 状态转换测试覆盖率 100%（所有状态 × 所有触发事件）
- 重启恢复测试通过（kill -9 模拟后重启验证）
- 并发安全测试通过（10 协程同时更新 1 个任务，无数据损坏）
- `Task.cancel()` 后，关联的 asyncio.Event 在 100ms 内被设置

#### 完成边界

`core/task_api.py`、`core/task_state_machine.py`、`core/session_manager.py`，每个文件有对应的 `tests/test_*.py`。

---

### 代码审查提示词（质量）

检查项：
1. 状态机的状态和事件是否用 Enum 定义，不允许使用字符串字面量
2. SQLite 操作是否使用了参数化查询，无 SQL 注入风险
3. 乐观锁的实现是否正确：UPDATE 时检查 version，失败后重新 SELECT 再试
4. asyncio.Event 是否在所有退出路径上被 set（包括异常路径），防止协程永久阻塞

---

### 代码审查提示词（性能）

检查项：
1. SQLite 连接是否使用了连接池或单连接复用（WAL 模式下单连接写入性能最优）
2. 状态变更的写入是否使用了批量事务（同一操作内的多次 UPDATE 合并为一个事务）
3. 重启恢复时，是否一次性加载所有未完成任务而非逐条查询
4. 乐观锁重试是否有上限（防止死循环）

---

### 代码审查提示词（复用性）

检查项：
1. 状态机的转换规则是否与业务逻辑解耦（通过配置或注册模式，而非 if-else）
2. Session Manager 的接口是否允许未来切换到 PostgreSQL 或其他存储
3. Task API 是否只暴露必要的公共方法，内部状态机实现细节不泄露

## F4：工具注册 + Schema 校验 + 工具执行器

### 开发提示词

#### 目标
实现 Tool Registry（工具注册中心）、Schema Validator（参数校验器）和 Tool Executor（工具执行器）。Registry 管理工具白名单和元数据，Validator 基于 JSON Schema 校验模型输出的参数，Executor 负责调用工具并处理超时、重试、取消和执行回执。

#### 判断标准

1. 工具注册时必须提供：名称、参数 JSON Schema、权限等级（R0-R3）、超时时间、重试预算和幂等键生成函数
2. Schema Validator 支持：类型校验、必填字段、枚举值、数值范围、字符串模式
3. Tool Executor 的执行流程：幂等键检查→超时控制→调用→回执校验→结果记录，任何一步失败都有明确的错误类型
4. 未注册工具的调用请求被拒绝，拒绝事件记入审计日志
5. 执行回执包含：工具名称、实际参数、执行时间、成功/失败、输出摘要和后续操作建议

#### 证据要求

- 注册 5 个模拟工具（file_open / knowledge_query / reminder_create / text_polish / meeting_process），每个有不同的权限等级和 Schema
- Schema 校验测试覆盖 20+ 种非法参数组合
- 超时测试：模拟一个 5 秒超时的工具，验证 Executor 在超时后取消并返回超时错误
- 幂等测试：同一幂等键的两次调用，第二次直接返回第一次的结果不重复执行
- 回执测试：工具返回不符合回执 Schema 时，Executor 标记为执行失败（非成功）

#### 权限边界

- 工具代码不得直接访问文件系统、网络或数据库（使用依赖注入的抽象接口）
- Registry 的注册方法不允许在运行时动态注册（必须在启动时完成，或通过受控的管理接口）
- Executor 不对工具的内部实现做任何假设，只依赖回执 Schema 判断成功

#### 停止条件

- 5 个模拟工具全部注册并可通过 Registry 查询
- 全部 Schema 校验测试通过
- 超时/幂等/回执测试通过
- 未注册工具调用被拒绝并生成审计事件

#### 完成边界

`core/tool_registry.py`、`core/schema_validator.py`、`core/tool_executor.py`，每个 200 行以内。

---

### 代码审查提示词（质量）

检查项：
1. Schema Validator 的错误信息是否包含：哪个字段、期望什么、实际是什么、修复建议
2. Tool Executor 的超时实现是否正确（使用 asyncio.wait_for + 取消传播）
3. 幂等键的生成是否由工具提供者定义（而非 Executor 猜测），不同工具的幂等键逻辑是否隔离
4. 回执校验是否区分了「回执格式错误」和「工具执行失败」

---

### 代码审查提示词（性能）

检查项：
1. Schema 校验是否在工具调用前完成（不浪费执行资源在非法参数上）
2. 工具注册表是否使用了字典/O(1) 查找，工具数量增长后性能不退化
3. 幂等键的存储是否有过期机制（防止无限增长）

---

### 代码审查提示词（复用性）

检查项：
1. 工具的抽象接口（F1 中定义）是否足够通用，能覆盖文件操作、知识检索、API 调用等不同类型
2. 注册中心的元数据 Schema 是否支持未来扩展（如新增风险等级、硬件依赖标记）
3. Executor 的回执处理逻辑是否与具体工具解耦

## F5：权限引擎 + 数据分级服务

### 开发提示词

#### 目标
实现 Policy Engine（权限与风险引擎）和 Data Classification Service（数据分级与脱敏服务）。Policy Engine 执行权限检查、风险评级和确认规则。Data Classification 实现 D0-D3 四级数据分类、敏感字段识别、脱敏策略和禁止外发清单。

#### 判断标准

1. Policy Engine 支持：角色检查、数据域检查、风险等级判定和确认页面生成
2. R3 级高风险动作必须触发二次确认，确认页面包含对象、内容、金额、影响和可撤销说明
3. Data Classification 实现正则模式匹配（手机号、身份证、邮箱、API Key 模式）+ 字段名匹配（password / token / secret 等）
4. D3 数据在任何情况下不进入模型上下文，不写入日志，不外发。在传给模型前被替换为 `[REDACTED]`
5. 脱敏策略可配置：D1 替换为类型标签，D2 默认不上云，D3 硬编码禁止

#### 证据要求

- Data Classification 的测试包含 50+ 条精心构造的样本（涵盖 D0-D3 混合文本、边界情况、误报风险）
- D3 检测的误报率测试：正常文本不应被误判为 D3
- Policy Engine 的测试覆盖所有角色 × 数据域 × 风险等级的组合
- 禁止外发清单的测试：即使路由决策为本地→云端，D3 数据仍然被拦截

#### 权限边界

- Data Classification 不依赖模型进行判定（使用确定性规则 + 正则），但保留模型辅助接口
- Policy Engine 的角色和数据域定义从配置文件加载，不允许硬编码
- 不实现用户认证系统（这是一个外部依赖，F5 只消费认证结果）

#### 停止条件

- Data Classification 的 50+ 测试样本全部正确分类
- 3 次脱敏测试（D1 替换 / D2 拦截 / D3 硬编码禁止）全部通过
- Policy Engine 的角色 × 风险矩阵测试 100% 通过
- D3 数据在任何测试中未出现在模型输入或日志中

#### 检索边界

中国个人信息的法定分类（《个人信息保护法》）仅作参考，本模块的分类体系以部署评估报告 §9 为准。

#### 完成边界

- 事实保护测试：输入包含电话号码和金额，验证输出中数值完全一致
- 语气调整测试：正式→随意，验证用词和句式变化
- 草稿标识测试：验证输出包含"草稿"标记

#### 权限边界

- 文本处理调用模型网关，不直接访问模型
- 事实字段的提取在发送给模型前完成（通过正则 + NER），不入模型上下文
- 正式发送后的文本记入审计日志，保留原始草稿和修改轨迹

#### 停止条件

- 4 种操作类型各 3 个测试用例全部通过
- 事实保护测试覆盖数字、日期、人名、专有名词
- 草稿标识和发送确认测试通过

#### 完成边界

`tools/text_processing_tool.py`，依赖 F2 ModelGateway。使用权限等级 R1。

质量：事实字段保护的提取逻辑是否准确（误保护率测试）、模型输出的后处理是否正确还原事实字段

## I1：Agent Core 集成

### 开发提示词

#### 目标
将 Phase 1 全部基础模块和 Phase 2 全部工具集成为一个完整的 Agent Core。实现架构文档 §6 的 7 步标准执行流程：用户输入→模型理解→Schema 校验→权限检查→参数确认→工具执行→结果交付。不新建模块，只做集成和编排。

#### 判断标准

1. 端到端流程：输入自然语言请求→输出执行结果和审计日志
2. 7 步流程中任何一步失败都有明确的错误信息和恢复路径
3. 任务状态在每一步都更新并持久化
4. 支持 5 种工具的正确选择和执行
5. 确认流程：多候选/缺失参数/高风险动作时暂停等待用户确认

#### 证据要求

- 5 个端到端测试用例（每种工具一个），全链路通过
- 2 个异常路径测试：模型返回非法 JSON / 工具执行超时
- 确认流程测试：文件查找返回 3 个候选，Agent 暂停等待确认
- 审计日志测试：端到端任务产生完整的审计事件链

#### 权限边界

- Agent Core 不绕过任何基础模块的安全检查（权限、数据分级、路由）
- 集成代码不直接访问 SQLite、文件系统或网络（全部通过已有模块的接口）
- 用户确认的交互界面通过回调接口提供，Agent Core 不实现 UI

#### 停止条件

- 5 个端到端测试全部通过
- 2 个异常路径测试通过
- 确认流程测试通过
- 7 步流程的每一步都有对应的审计事件

#### 完成边界

`core/agent_core.py`，约 300 行。集成代码只做编排，不包含业务逻辑。

---

### 代码审查提示词

质量：编排代码是否正确处理了每个模块的异常、7 步流程是否可单步调试
性能：端到端延迟的瓶颈在哪一步（期望 MockAdapter 下 < 100ms）
复用性：编排逻辑是否与具体工具解耦（工具列表可配置）

## I2：FastAPI 服务封装

### 开发提示词

#### 目标
将 Agent Core 封装为 FastAPI HTTP 服务。提供 RESTful API 接口：创建任务、查询任务状态、确认/取消任务、获取审计日志。为后续文字界面和语音界面提供统一的 API 层。

#### 判断标准

1. API 端点：POST /tasks（创建）、GET /tasks/{id}（查询）、POST /tasks/{id}/confirm（确认）、POST /tasks/{id}/cancel（取消）、GET /tasks/{id}/audit（审计日志）
2. 请求和响应使用 F1 定义的 Pydantic 模型
3. 支持 Server-Sent Events（SSE）推送任务状态变更
4. API 错误返回统一的 ErrorResponse 格式
5. OpenAPI 文档可通过 /docs 访问

#### 证据要求

- 使用 pytest + httpx.AsyncClient 编写 API 集成测试
- 创建任务→查询状态→确认→查看结果，全链路 API 测试通过
- SSE 测试：客户端连接后，任务状态变更在 500ms 内推送
- 错误测试：非法请求返回 422、任务不存在返回 404、权限不足返回 403

#### 权限边界

- API 不实现用户认证（由外部认证代理处理），但预留认证中间件接口
- 审计日志 API 只返回当前会话的任务，不允许跨任务查询
- 不通过 API 暴露内部模块的直接调用（如直接调 ModelGateway）

#### 停止条件

- 全链路 API 测试通过
- SSE 推送测试通过
- 错误处理测试通过
- OpenAPI 文档完整且可访问

#### 完成边界

`api/server.py`、`api/routes.py`、`api/middleware.py`。FastAPI 应用在 `api/__init__.py` 中创建。

---

### 代码审查提示词

质量：异常处理的中间件是否覆盖了所有 Agent 异常类型、SSE 连接断开后是否正确清理
性能：并发请求下的任务隔离、SSE 连接数的上限控制
复用性：路由是否模块化（后续新增 API 版本时不影响现有路由）

## I3：自动化评测集

### 开发提示词

#### 目标
建立完整的自动化评测集，覆盖意图识别、参数提取、工具选择、Schema 合规和端到端任务执行。评测集同时支持 MockAdapter（快速回归）和 CloudAdapter（真实模型评测），确保更换模型后可一键回归。

#### 判断标准

1. 评测集包含至少 50 个固定测试用例，覆盖 5 种工具和 3+ 种异常场景
2. 每个测试用例包含：输入文本、期望意图、期望参数、期望工具、允许的容差
3. 评测支持两种模式：mock（秒级完成）和 cloud（真实模型，分钟级）
4. 评测报告自动生成，包含分维度准确率、失败用例详情和与上一版的差异对比
5. 评测集格式与模型无关，后续接入 Qwen 直接复用

#### 证据要求

- 50 个测试用例全部在 mock 模式下通过
- Cloud 模式下的评测报告包含延迟分布（P50/P95/P99）
- 模拟一次"模型退化"（修改 MockAdapter 使其输出错误），验证评测能捕获退化
- 评测报告包含与上一版的 diff 对比

#### 权限边界

- 评测集的输入文本不包含真实用户数据
- Cloud 模式的 API 调用有速率限制（避免意外消耗费用）
- 评测报告不包含模型返回的完整文本（只包含统计和失败摘要）

#### 停止条件

- 50 用例在 mock 模式全部通过
- 模型退化检测测试通过
- 评测报告格式完整且包含 diff 对比

#### 完成边界

`evaluation/test_cases/` 下 5 个 JSON 文件（每种工具一个），`evaluation/runner.py`，`evaluation/report_generator.py`。

---

### 代码审查提示词

质量：测试用例的覆盖度（是否覆盖边界情况、异常输入、多语言混合）
性能：50 用例的 mock 模式执行时间（目标 < 5 秒）
复用性：评测集的格式是否与具体工具实现解耦

```
F1 ─┐
```

每个 F 模块完成后，并行启动 3 个审查子 Agent（质量/性能/复用性）。

### Phase 2 并行派发（5 个子 Agent）

```
T1 ─┐

T4 ─┤
T5 ─┘
```

每个 T 模块完成后，并行启动 3 个审查子 Agent。

### Phase 3 顺序执行

```
I1 → I2 → I3 （逐层依赖）
```

每个 I 模块完成后，并行启动 3 个审查子 Agent。

### 总子 Agent 估算

- 开发：8 (F) + 5 (T) + 3 (I) = 16 个
- 审查：16 × 3 = 48 个
- 合计：64 个子 Agent 调用
