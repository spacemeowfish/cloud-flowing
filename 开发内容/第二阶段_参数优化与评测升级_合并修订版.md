# Qwen2.5-3B-Instruct 参数优化与评测升级（开发提示词 v2）

> 替代此前两份第二阶段提示词及其首版合并稿。
> 本任务只优化模型输出的理解、参数规范化和评测，不改变产品功能范围。

将本文件完整交给 Codex 作为开发任务。先阅读全部约束，再开始编辑代码。

---

## 目标

在不降低 DeepSeek 当前表现、不绕过权限与确认流程的前提下，提升 `Qwen2.5-3B-Instruct` 在固定评测集上的任务参数处理能力，并把评测拆为以下互不混淆的层次：

1. 原始模型输出：模型直接生成的意图和参数。
2. 规范化后输出：确定性、可审计规则修复后的参数。
3. 端到端可执行性：经过 Schema、Policy、Router 和 Dry-run Tool 后的安全结果。

验收目标：Qwen 的 `end_to_end_accuracy >= 90%`。此指标定义为：

```text
intent_ok
AND tool_ok
AND normalized_contract_ok
AND semantic_status == match
AND expected_pipeline_outcome_ok
```

其中 `expected_pipeline_outcome_ok` 指正确执行无副作用，或对高风险动作正确进入确认态；它不代表自动执行删除等高风险行为。

## 不可违反的架构约束

1. **所有会改变动作、ID、路径或风险级别的修复，必须发生在 Tool Schema 校验和 Policy 判定之前。**
   严禁在工具 `execute()` 中把 `create/query/cancel` 改为 `delete_all`，也严禁在 `execute()` 中补写路径或提醒 ID。

2. 参数规范化器必须接收：`intent`、模型 `arguments`、以及未经模型改写的 `task.request_text`。它返回新字典和变更记录，绝不原地修改输入。

3. 归一化后的参数必须先通过 Tool Schema，再进入 Policy。若归一化得到 `action=delete_all`，现有 R3 删除全部确认必须照常触发；未确认时不得调用工具。

4. `ToolMetadata.parameters_schema` 是**工具执行参数**的唯一权威来源。模型接收 Schema 不得手工复制五份工具 Schema；如需限制模型字段，必须从已注册工具 metadata 在运行时生成投影 Schema，并且它只能比执行 Schema 宽松到允许明确列出的原始字段别名。

5. 结构化输出约束是校验，不是模型纠错机制。`CloudModelAdapter` 只能校验 JSON 外壳和模型接收 Schema，绝不能在归一化前应用严格执行 Schema。模型输出不合法时：
   - 在线任务：记录审计事件、任务失败或进入补充确认，绝不执行工具。
   - 评测：将该用例记为 `model_schema_invalid`，继续后续用例，整轮评测不得中断。

6. 评测端到端流程必须使用隔离容器、临时数据库、临时目录和 Dry-run 工具。不得修改真实提醒库、打开真实文件、删除真实数据，也不得自动批准高风险确认。

7. 不使用另一个 LLM 给模型判分。语义判断只能使用确定性归一化和评测前锁定的 aliases。

## 第一阶段：执行契约与模型输出 Schema

### 1.1 补齐工具的真实执行契约

先审阅每个 `ToolMetadata.parameters_schema`，并用测试固定以下条件：

- `reminder_create.action` 只能为 `create | query | cancel | complete | delete_all`。
- `cancel` 与 `complete` 必须提供正整数 `id`。
- `query` 的 `scope` 只能为 `next_7_days | overdue`，缺省时使用工具既有默认值。
- `create` 的必填字段以现有补充确认机制为准：缺参时不执行，返回或进入 `missing_fields` 确认态。
- `meeting_process.source_path` 是绝对路径字符串，执行前仍必须由工具验证扩展名、授权根目录和文件存在性。
- `text_polish` 保留现有的 `confirm_send`、`tone`、`target_length` 等工具能力；不要因为模型首轮通常不用就从工具 Schema 删除。

对提醒的条件必填约束使用 JSON Schema `if/then`，或在统一的契约校验器中明确实现并测试。不得仅依赖 `action` 是必填字段就声称“可执行”。

### 1.2 运行时生成两层输出 Schema

新增一个 Schema builder，例如：

```python
build_model_acceptance_schema(registry: ToolRegistry) -> dict
```

它从注册工具 metadata 生成五个 intent 分支，并通过顶层 `oneOf` 将 `intent: const` 与对应 `arguments` 绑定。不得在 `models/model.py` 维护第二份 `INTENT_ARGUMENTS_SCHEMA`。

模型接收 Schema 只验证 JSON 外壳、intent、字段类型和字段白名单；它**不等同于**工具执行 Schema。除工具的规范字段外，只允许以下原始别名：

- `knowledge_query.arguments.question`
- `file_open.arguments.keyword`

其他未声明字段仍使用 `additionalProperties=false` 拒绝。模型接收 Schema 必须允许上述别名分支到达归一化器；归一化器完成后，再以 `ToolMetadata.parameters_schema` 进行严格执行校验。

每个 intent 的模型接收分支区分两种状态：

1. **完整候选分支**：`missing_fields=[]`，arguments 包含足以经归一化后满足执行契约的字段。
2. **待补充分支**：`missing_fields` 非空，arguments 只允许该工具已声明的字段或上述别名，但不强制尚未提供的字段；任务必须在严格执行 Schema/Policy 前进入补充确认，不得执行。

两种分支都必须 `additionalProperties=false`。`question`、`keyword` 只能通过明确的模型接收别名分支到达归一化器，归一化后绝不能遗留到工具执行参数。

`CloudModelAdapter` 使用模型接收 Schema；`AgentCore` 在归一化后使用工具执行 Schema；评测服务分别记录两次校验结果。Schema builder 不能在 import 时实例化真实工具，也不能引入循环依赖。

## 第二阶段：校验前参数归一化

### 2.1 插入位置

在 `AgentCore._continue()` 中：读取 task 上下文后、调用 `SchemaValidator.validate()` 和 `PolicyEngine.evaluate()` 前执行归一化。规范化结果必须通过任务状态更新持久化，并写入审计事件，包含规则名称和变更前后字段名，不记录敏感原文。

推荐接口：

```python
@dataclass(frozen=True)
class NormalizationResult:
    arguments: dict[str, JsonValue]
    applied_rules: list[str]

def normalize_arguments(
    *, intent: str, arguments: Mapping[str, JsonValue], request_text: str
) -> NormalizationResult: ...
```

### 2.2 允许的确定性规则

规则按 intent 白名单生效，并要求新增正反例测试：

| Intent | 规则 | 边界 |
|---|---|---|
| `knowledge_query` | `question -> query`，仅当没有 `query` 时 | 不改写查询内容 |
| `file_open` | `keyword -> query`，仅当没有 `query` 时 | 不伪造路径或候选文件 |
| `meeting_process` | 从原始请求提取一个明确的 Windows 或 POSIX 绝对路径；若模型值缺失或与原文中唯一绝对路径不一致，则以原文为准 | 多路径或无路径时不猜测，转 `missing_fields` |
| `reminder_create` | 原文完全匹配“取消提醒 + 正整数”时设为 `cancel` 和该 ID；原文明确含“删除所有提醒”“删除全部提醒”或“清空提醒”时设为 `delete_all` | “取消提醒 12 月 5 日的会议”不是 ID 12；任何动作改写都必须发生在 Policy 前 |
| `text_polish` | 原文以“缩写”“总结”开头时，且模型未明确指定其他操作，可归为 `summarize` | 不对 `file_open` 等其他 intent 生效 |

不要在工具 `execute()` 中再做以上修复。工具只负责执行已验证、已授权的参数。

### 2.3 Few-shot

在 `CloudModelAdapter` 的分类提示词中加入不超过 8 条完整、可解析、可通过运行时 Schema 的示例。示例覆盖下列行为，不宣称一条示例等于一个失败用例：

- 找会议记录 -> `file_open.query`
- 知识库查询 -> `knowledge_query.query`
- 完整 Windows 路径会议纪要 -> `meeting_process.source_path`
- 查看未来 7 天待办 -> `reminder_create.query + scope`
- 取消提醒 12 -> `reminder_create.cancel + id`
- 删除所有提醒 -> `reminder_create.delete_all`
- 缩写或总结 -> `text_polish.summarize`
- 日程创建 -> `reminder_create.create + text + when`

每条示例必须包含完整的 `intent`、`arguments`、`missing_fields`、`confidence`，不得使用 `...` 省略字段。不要把全部 Schema 原文重复粘进 prompt；使用紧凑字段表和少量示例，避免挤占 Qwen2.5-3B-Instruct 的有效上下文。

## 第三阶段：双层评测

### 3.1 固定原始输出快照

新增可重放的原始快照格式，每条记录至少包括：

```json
{
  "case_id": "knowledge-04",
  "input_hash": "...",
  "provider": "ollama",
  "model": "qwen2.5:3b-instruct-q4_K_M",
  "prompt_version": "...",
  "raw_result": {"intent": "knowledge_query", "arguments": {"query": "公司报销标准"}},
  "model_error": null,
  "latency_ms": 0
}
```

若模型结构不合法，保存 `model_error`，不伪造 `raw_result`。快照用于让旧、新评分器针对**同一输出**重放，避免把模型波动误认为评分器改进。

aliases 根据用户原句、期望业务效果和评测规范人工预登记，并在首次正式快照前锁定。不得根据同一快照中的 Qwen 失败结果补 aliases。若需要从历史失败中设计 aliases 或规则，必须新增并冻结一份独立留出集来验收。

### 3.2 原始输出评分

保留既有 `argument_accuracy` 的定义和输出格式，作为兼容指标，不重新赋义。

新增但不替换以下指标：

- `raw_intent_accuracy`
- `raw_tool_accuracy`
- `raw_contract_accuracy`
- `raw_exact_argument_accuracy`
- `model_schema_invalid_count`

原始输出的契约校验基于模型选择的 intent 对应工具 Schema。错误 intent 仍可有 `raw_contract_ok=true`，但不能被记为端到端成功。

### 3.3 隔离的端到端 Dry-run 评分

新增 `EvaluationDryRunContainer`：

- 使用临时 SQLite 数据库、临时授权根目录、测试时钟和无副作用的 Tool 实现。
- Tool metadata 与生产工具一致，Dry-run Tool 只返回模拟 `ToolReceipt`。
- 保留 Agent Core、Schema Validator、Policy Engine、Router、Tool Executor 的调用顺序。
- 对 `delete_all` 等 R3 动作，断言任务进入 `awaiting_confirmation`；评测不得调用 `confirm(approved=true)`。
- 对缺参请求，断言任务进入缺字段确认态，而非执行工具。

端到端报告必须分别记录：模型原始 arguments、规范化后的 arguments、规范化规则、任务最终状态、是否通过 Schema、Policy 决策和实际/模拟工具名。敏感字段按现有审计规范脱敏。

### 3.4 语义判定与统计

`semantic_match.py` 返回显式枚举：`match | mismatch | needs_review`，不得以 `(bool, reason)` 混用三态。

规则顺序：

1. `meeting_process.source_path`、`reminder_create.action/id`、`text_polish.operation` 严格完全一致。
2. `knowledge_query.query` 和 `file_open.query` 仅允许保守归一化后完全一致，或命中预登记 field-level aliases。
3. 不使用子串阈值，不猜测词义，不读取真实文件系统。
4. 缺字段、未知差异和无法确定的情况标记为 `needs_review`。

报告同时给出：

```text
semantic_match_rate = match / total
semantic_adjudicated_accuracy = match / (match + mismatch)
semantic_coverage = (match + mismatch) / total
needs_review_count
```

`end_to_end_accuracy` 始终以全部用例为分母，`needs_review` 不得被计为端到端成功。

## 第四阶段：报告、CLI 与回归

`--detailed` 启用双层报告；未传该参数时保持旧评测格式和语义不变。

新增 CLI 选项：

```text
agent-platform evaluate --capture-raw <path>
agent-platform evaluate --detailed --raw-snapshot <path> --output <path>
```

`evaluation/compare_reports.py` 必须支持新旧报告并存，禁止将不同含义的 `argument_accuracy` 直接相减。实际报告生成代码位于 `agent_platform/evaluation/report_generator.py`，兼容导出模块无需承载新逻辑。

建议验证顺序：

```powershell
# 1. 在依赖齐全且配置已冻结的环境中，捕获一次 Qwen 原始输出
Copy-Item .env.qwen .env -Force
agent-platform evaluate --mode cloud --capture-raw evaluation/reports/qwen_before_raw.jsonl

# 2. 对同一快照运行新评分器，作为评分器基线
agent-platform evaluate --detailed --raw-snapshot evaluation/reports/qwen_before_raw.jsonl --output evaluation/reports/qwen_before_scored.json

# 3. 实施优化后重新捕获，并运行隔离 Dry-run 端到端评测
agent-platform evaluate --mode cloud --capture-raw evaluation/reports/qwen_after_raw.jsonl
agent-platform evaluate --detailed --raw-snapshot evaluation/reports/qwen_after_raw.jsonl --output evaluation/reports/qwen_after.json

# 4. 使用相同数据集、提示词版本记录和报告口径进行 DeepSeek 回归
Copy-Item .env.deepseek .env -Force
agent-platform evaluate --mode cloud --detailed --output evaluation/reports/deepseek_after.json
```

`agent-platform evaluate` 自行创建容器，不要在此流程中启动 `agent-platform serve`。

## 验收与停止条件

必须同时满足：

1. Qwen `end_to_end_accuracy >= 90%`，且报告完整显示原始、规范化和端到端三个层级。
2. DeepSeek 在相同数据集、模型配置和指标定义下没有回归；如有波动，列出具体 case 和原始快照证据。
3. 所有既有测试在依赖齐全的基线环境中通过，并新增以下回归测试：
   - `question -> query` 仅在知识库意图生效。
   - 损坏路径由原文唯一绝对路径修复；多路径不猜测。
   - `取消提醒 12` 正确取消；“取消提醒 12 月 5 日的会议”不误判 ID。
   - `delete_all` 经归一化后仍触发 R3 确认，且未确认时 Dry-run Tool 从未被调用。
   - 非法模型 JSON 只失败当前用例，50 条评测仍能完成。
   - `needs_review` 同时反映在 match rate、coverage 和端到端分母中。
4. 不因新增 Schema 删除现有工具字段或破坏缺字段确认流程。

若连续三轮在冻结数据集和配置下没有改善，停止调 prompt，报告保留失败模式、规则覆盖情况、原始快照和是否需要更大模型或微调的结论。
