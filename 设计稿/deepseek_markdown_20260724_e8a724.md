# 基于RK3588的多端互联AI语音助手
## 产品需求与设计规格书（PRDS）

**版本**：V1.0  
**日期**：2026年7月24日  
**状态**：需求锁定（Ready for MVP开发）

---

## 一、项目概述与产品定位

### 1.1 项目背景
本项目旨在利用RK3588开发板的高性能NPU（6TOPS）及多屏显示能力，打造一款区别于市面通用智能音箱（如小爱同学）的 **“AI数字替身助理”**。

### 1.2 核心差异化定位
- **不与小爱同学竞争物理世界（智能家居）**：在家居控制领域，本设备默认采取“礼让策略”，不抢答、不接入复杂的厂商生态。
- **专注数字世界（PC/手机）**：核心价值在于通过模拟操作或API接口，替用户完成电脑端的文件整理、消息发送、报表传输等高复杂度办公任务。
- **混合算力架构**：本地跑轻量模型（Qwen 1.5B）保证基础隐私与断网可用，云端调用大模型处理复杂逻辑。

## 二、需求决策追踪（为什么这么做？）

本规格书的每一处设计均基于实际场景的痛点推演，关键决策点如下：

| 维度 | 最终决策 | 决策依据（用户场景） |
| :--- | :--- | :--- |
| **远场拾音** | 4-6麦PDM环形阵列 | 覆盖100㎡房间，配合波束成形实现10米唤醒。 |
| **敏感操作安全** | **语音发起 + 屏幕点按确认** | 杜绝“支付、发消息”因误识别导致的不可逆后果，物理触控作为终极安全锁。 |
| **PC操控方式** | PC端Agent + 云端API直传（无头模式） | 优先保证不打断电脑前台用户，后台完成文件分发。 |
| **多用户识别** | **本地声纹锁（强制注册）** | 区分主人与访客，防止文件发错人或误删他人资料。 |
| **断网/离线处理** | **本地任务队列 + 断连红温指示** | 断网时本地模型保底（闹钟/备忘录），PC离线时指令落盘，上线后自动补执行。 |
| **系统底层** | **Ubuntu 22.04 / 24.04** | RKLLM-Toolkit支持最完善，便于部署大模型及Python库调用。 |

## 三、硬件架构选型清单

| 组件 | 推荐型号/规格 | 关键备注 |
| :--- | :--- | :--- |
| **核心主板** | RK3588（如Radxa Rock 5B+ / Orange Pi 5 Plus） | **必须配置16GB LPDDR4X**，以满足1.5B模型（~1.2GB）+ 系统开销。 |
| **麦克风阵列** | 4-6麦PDM环形阵列 | 通过GPIO连接，需支持多通道同时录音。 |
| **音频输出** | I2S数字功放 + 全频扬声器单元 | 用于语音播报及提示音。 |
| **交互屏幕** | **5寸~7寸 MIPI-DSI 电容触摸屏** | 用于展示任务进度、作为“安全确认”按钮的物理载体。 |
| **散热方案** | 主动散热（涡轮风扇 + 散热鳍片） | RK3588满载约8-10W，插电场景必须配备主动散热以保证NPU性能全开（暂不优先考虑静音降频）。 |
| **状态指示灯** | 可编程RGB LED灯带 | 用于“离线红温警告”、“任务处理中”等视觉反馈。 |

## 四、软件功能模块与部署切割清单

| 模块 | 部署位置 | 核心技术选型/实现方案 |
| :--- | :--- | :--- |
| **语音唤醒与采集** | RK3588（本地） | 使用轻量级DNN模型+MFCC特征，实现Always-on低功耗监听（<180ms响应）。 |
| **声纹识别（必选）** | RK3588（本地 NPU） | 部署ECAPA-TDNN轻量模型，首次使用需录入3句语音注册，识别准确率>95%。 |
| **本地推理引擎** | RK3588（本地 NPU） | **Qwen2.5-1.5B-Instruct (INT4量化)**，使用RKLLM-Toolkit转换，负责闹钟、备忘录、离线宏指令。 |
| **云端大模型** | 公有云API | 兼容OpenAI接口协议（预留接入DeepSeek/通义千问等），处理多轮复杂推理。 |
| **PC端受控Agent** | 用户电脑端 (Win/Mac) | **Python开发**。功能：①监听系统通知 ②无头模式上传文件至云盘生成链接 ③模拟键鼠操作（PyAutoGUI）。 |
| **手机端远程控制** | 手机（微信小程序/Flutter） | 发送文字指令、查看任务进度、开启“静默模式”。 |
| **多端消息中枢** | RK3588（本地） | **MQTT Broker (Mosquitto)**，负责协调手机、PC、设备本体的消息广播。 |
| **离线任务队列** | RK3588（本地存储） | SQLite数据库存储指令，状态机包含：待执行 → 执行中 → 成功/失败。 |

## 五、核心场景状态机流转图（用户体验剧本）

### 场景A：安全敏感操作（如“把报表发给老板”）
1. **拾音与唤醒** → 声纹比对（确认主人）。
2. **意图路由** → 本地模型识别为“敏感文件发送”。
3. **任务执行** → 通知PC Agent后台打包上传文件生成链接。
4. **安全阻塞（关键）** → **屏幕亮起显示：“即将发送[报表]给[老板]，请点击确认”**。
5. **用户操作** → 用户伸手**物理触摸点击屏幕按钮**。
6. **结果反馈** → 语音极低声播报：“已发送”，屏幕显示对勾。

### 场景B：PC离线时的补执行机制
1. **指令下发** → 用户说“整理下载文件夹”。
2. **状态探测** → 检测到PC Agent心跳超时（离线）。
3. **即时反馈** → 语音播报：“收到，电脑当前离线，任务已记录，上线后自动执行”。
4. **持久化** → 指令写入SQLite，状态标记为`PENDING`。
5. **补执行** → PC上线Agent重连，RK3588下发指令，静默执行。
6. **完成提醒** → 屏幕闪烁提示：“昨日的离线整理任务已完成。”

### 场景C：智能家居（与小爱共存）
1. **用户说“关灯”** → 设备拾音，声纹比对失败（或非主人）。
2. **领域分类** → 本地模型识别为“智能家居”类目。
3. **礼让策略** → 设备**完全静默、指示灯熄灭**，主动让出麦克风权限。
4. **兜底检测** → 3秒后若检测到灯未关闭（MQTT未收到状态变更），才极低声询问：“小爱无响应，是否需要我帮忙？”

## 六、安全与容错机制设计

| 机制 | 具体实现 |
| :--- | :--- |
| **双重确认锁** | 涉及“支付、删除、发送消息”时，必须通过**屏幕物理点击确认**，语音确认无效。 |
| **网络断联容错** | ① 机身LED灯带变为**红色呼吸灯**提醒。 ② 云端API不可用时，自动降级至本地1.5B模型。 |
| **声纹权限分级** | 主人声纹：拥有全部PC操控权限。访客/家人声纹：仅限查天气、设闹钟，无法触碰电脑文件。 |
| **PC Agent看门狗** | 若Agent崩溃，RK3588会检测到心跳超时，自动将后续指令存入队列，避免指令丢失。 |

## 七、MVP（最小可行性产品）开发路线图

为避免资源浪费，建议按如下四个阶段分批交付：

- **Phase 1（硬件平台与基础链路）**  
  RK3588刷Ubuntu，点亮DSI触摸屏，跑通4麦阵列的`arecord`录音及播放，验证散热方案有效性。

- **Phase 2（AI核心能力）**  
  部署Qwen1.5B（RKLLM转换），跑通“语音→本地模型→指令解析→屏幕显示文字”的最简闭环。

- **Phase 3（核心差异功能）**  
  开发PC端Agent MVP（仅支持后台云盘上传+文件移动），打通RK3588到PC的Socket通信，实现“语音发文件”Demo。

- **Phase 4（全场景覆盖）**  
  集成声纹模块、离线任务队列（SQLite）、MQTT中枢及手机App雏形。

## 八、附录：开发风险提示

1. **PDM时钟同步**  
   多麦克风阵列的时钟同步是难点，务必在硬件设计时预留足够的GPIO引脚，并提前确认开发板DTS（设备树）对多PDM通道的支持情况。

2. **RKLLM量化精度**  
   Qwen1.5B 4bit量化后可能丢失部分逻辑推理能力，需提前准备测试集验证“意图分类”的准确率是否达标。

3. **PC端兼容性**  
   Windows上的PyAutoGUI可能受UAC（用户账户控制）弹窗影响，PC端Agent建议以管理员权限运行。
